# 链路追踪

网关作为调用链的第一跳，可以把一次请求从入口贯通到上游服务，并按需把耗时上报到已有的 APM。

默认关闭，不改现有访问日志和内部 `trace_id`。开启后只多做两件事：识别/生成 W3C `traceparent`，以及（可选）用 OTLP 把 Span 发给 Collector 或云厂商的 OTLP 接入点。

**网关只认 OTLP。** SkyWalking、腾讯云 APM、阿里云 ARMS、Jaeger、Tempo 都接在 Collector（或对方提供的 OTLP 入口）后面，不要把 SkyWalking OAP、云厂商控制台里的非 OTLP 地址写进网关。

---

## 实际产品是否支持

| 产品 | 是否支持 | 怎么接 |
|------|----------|--------|
| Apache SkyWalking 9.3+ | 支持 | Collector `skywalking` exporter 到 OAP `:11800`，或 OAP 打开 `receiver-otel` 收 OTLP |
| Jaeger 1.46+ / Jaeger v2 | 支持 | Collector `otlp` 到 Jaeger `:4317`；Jaeger 也可直接当 OTLP 入口 |
| Grafana Tempo | 支持 | Collector `otlp` 到 Tempo 的 OTLP 端口 |
| 腾讯云 APM | 支持 | 控制台选 **OpenTelemetry**，把接入点和 Token 配在 **Collector**，不要配 SkyWalking/Jaeger 协议 |
| 阿里云 ARMS（可观测链路 OpenTelemetry 版） | 支持 | 同上，用控制台给出的 OTLP 地址 + 鉴权头 |
| Zipkin | 支持 | Collector `zipkin` exporter 做协议转换 |
| SkyWalking-Go Agent（`-toolexec`） | **不支持** | 覆盖不了自研 Handler，也会把网关绑死在 SkyWalking |
| 直连 SkyWalking OAP 的原生协议（非 OTLP） | **不支持** | 网关没有 SkyWalking SDK |

换 APM 只改 Collector 的 exporter，网关的 `app.tracing` 保持 `endpoint = Collector:4317` 即可。

在 APM 界面里应能看到：

- 服务名：`app.tracing.service_name`（默认 `gateway`）
- 操作/Span：`gateway.request`、`gateway.auth`、`gateway.ratelimit`、`gateway.proxy`
- 属性：`gateway.trace_id`（等于访问日志里的 `trace_id`）、`http.route`、`http.response.status_code`

## 架构

```text
客户端
  │  traceparent（有则续，无则新建）
  ▼
网关数据面
  · 内部 trace_id 继续写访问日志 / 后端追踪日志（不变）
  · Span 属性带上 gateway.trace_id，方便和日志互查
  · 转向上游时注入 traceparent
  · 异步 OTLP 导出（失败可丢，不堵请求）
  ▼
OpenTelemetry Collector（推荐外置）
  ▼
SkyWalking / 腾讯云 APM / 阿里云 ARMS / Jaeger / Tempo
```

`tracing.Tracer` 在进程启动时创建一次。改 `app.tracing` 后必须重启网关进程；路由热加载不会重建它。

## 配置

写在 `configs/app.yaml` 的 `app.tracing`。进程级：数据面和管理端共用。不要写到已弃用的 `configs/gateway.yaml`。

```yaml
app:
  tracing:
    enabled: false          # 总开关；false 时行为与接入前完全一致
    service_name: gateway   # APM 里显示的服务名
    service_version: ""     # 空则使用 app.version
    environment: ""         # APM 的 deployment.environment，例如 prod
    endpoint: ""            # Collector 或云厂商 OTLP 地址。留空=只传播 Header，不上报
    protocol: grpc          # grpc | http；TLS 用 grpcs 或 https
    sampling_rate: 0.1      # 新建 Trace 上报比例，见下方说明
    insecure: true          # 内网 / Sidecar Collector 用明文
    headers: {}             # OTLP 上报鉴权头，见下方示例；本机 Collector 保持空
```

### sampling_rate 是什么

控制**新请求要不要把 Span 报到 APM**，不是访问日志的采样。

写成 `0` 到 `1` 的小数，表示概率：

| 填写 | 实际含义 | 适用 |
|------|----------|------|
| `0.01` | 大约每 100 笔新请求里，1 笔上报 | 超高流量生产 |
| `0.1` | 大约每 10 笔里 1 笔上报（默认） | 一般生产 |
| `1` | 每笔都上报 | 本机排查，不要长期开在生产 |

下面这些**不受** `sampling_rate` 影响，每笔请求都会做：

- 访问日志、后端追踪日志里的 `trace_id`
- 转向上游时写入 `traceparent`（链路还能串起来）
- 客户端已经带着「已采样」的 `traceparent` 时，本请求会跟着重报，避免一条链路中间缺网关这一跳

填 `0` 或负数会被改回默认 `0.1`。想完全关掉追踪，用 `enabled: false`。

### enabled 和 endpoint

| `enabled` | `endpoint` | 行为 |
|-----------|------------|------|
| false | 任意 | 空操作。客户端自带的 `traceparent` 仍可能被代理原样拷贝 |
| true | 空 | 识别/生成 `traceparent` 并注入上游，不上报 |
| true | 已填写 | 传播 + OTLP 导出 |

`endpoint` 只填主机和端口，不要带 `http://`。例如 `127.0.0.1:4317`、`otel-collector:4317`。配错时进程启动失败。

### headers 怎么配

`app.tracing.headers` 只会附加到**网关发给 Collector（或直连的 OTLP 接入点）的上报请求**上，用来做接入认证。它不是转给上游业务的 HTTP 头，也不是 `pass_headers`。

本机 / 内网 Collector 一般不鉴权，保持空即可：

```yaml
app:
  tracing:
    enabled: true
    endpoint: 127.0.0.1:4317
    protocol: grpc
    insecure: true
    headers: {}
```

Collector 自己开了接入 Token 时，写在网关：

```yaml
app:
  tracing:
    enabled: true
    endpoint: otel-collector:4317
    protocol: grpc
    insecure: true
    headers:
      Authorization: "Bearer 换成Collector的接入Token"
```

没有 Collector、网关直连云厂商 OTLP 时（不推荐，换云要改网关），头名以控制台为准。

腾讯云 APM（协议选 OpenTelemetry）：

```yaml
app:
  tracing:
    enabled: true
    endpoint: ap-guangzhou.apm.tencentcs.com:4317
    protocol: grpcs
    headers:
      Authorization: "Bearer 换成控制台的OTLP_Token"
```

阿里云 ARMS（可观测链路 OpenTelemetry 版，常见是 HTTP）：

```yaml
app:
  tracing:
    enabled: true
    endpoint: <控制台给出的主机:端口>
    protocol: https
    headers:
      Authentication: "换成控制台的鉴权值"
```

推荐做法：云厂商 Token 写在 **Collector 的 exporter.headers**，网关 `headers` 保持 `{}`，只指向内网 Collector。不要把 SkyWalking Java Agent / OAP 用户名密码写到这里。

## 最短接入（本机 Collector）

1. 起 Collector，监听 `4317`（OTLP gRPC）。
2. 改网关配置并**重启进程**：

```yaml
app:
  tracing:
    enabled: true
    service_name: gateway
    endpoint: 127.0.0.1:4317
    protocol: grpc
    sampling_rate: 0.1
    insecure: true
```

3. 看网关日志出现 `链路追踪已启用`。
4. 打一笔经过网关的请求，在 APM 里按服务名 `gateway` 查，应有 `gateway.request`。
5. 用访问日志里的 `trace_id` 在 APM 搜属性 `gateway.trace_id`，两边应对上。

## 对接实际产品

下面的 YAML 全部是 **OpenTelemetry Collector** 的配置（常见文件名 `otel-collector-config.yaml`），**不要写进网关的 `app.yaml`**。

网关只认识 Collector。三块的含义：

| 段 | 白话 | 本仓库怎么配 |
|----|------|--------------|
| `receivers` | 谁把数据发给 Collector | 固定收网关的 OTLP，监听 `4317` |
| `exporters` | Collector 再把数据发给谁 | 换成你的 APM 地址 |
| `service.pipelines.traces` | 把上面两段串起来 | `receivers → processors → exporters` |

换 APM 只改 `exporters` 和 pipeline 里的名字。网关始终是：

```yaml
endpoint: 127.0.0.1:4317   # 或 otel-collector:4317
protocol: grpc
```

本机可用官方镜像启动（把下面某一段存成 `otel-collector-config.yaml`）。`debug`、`otlp`、`otlphttp` 用核心镜像即可；`skywalking` exporter 必须换成 `otel/opentelemetry-collector-contrib`：

```bash
docker run --rm -p 4317:4317 \
  -v "$(pwd)/otel-collector-config.yaml:/etc/otelcol/config.yaml" \
  otel/opentelemetry-collector:latest
```

Windows PowerShell 把 `$(pwd)` 换成当前目录的绝对路径即可。

### 本机先看日志（不接 APM）

用来确认网关已经把 Span 打出来。Collector 标准发行版自带 `debug` exporter：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
processors:
  batch: {}
exporters:
  debug:
    verbosity: detailed
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [debug]
```

打一笔经过网关的请求后，Collector 控制台应出现 `gateway.request`。

### SkyWalking

把上一份里的 `debug` 换成 OAP。`oap.skywalking.svc:11800` 改成你的 OAP 地址：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
processors:
  batch: {}
exporters:
  skywalking:
    endpoint: oap.skywalking.svc:11800
    insecure: true
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [skywalking]
```

OAP 9.3+ 若已开启 `receiver-otel`，也可以把 `exporters` 改成 `otlp`，`endpoint` 填 OAP 的 OTLP 端口。不要对网关使用 `apache-skywalking-go-*.tgz`。

### 腾讯云 APM

1. 腾讯云控制台 → 应用性能监控 → 应用接入 → 协议选 **OpenTelemetry**（不要选 SkyWalking / Jaeger）。
2. 复制 **OTLP 接入点**（一般是 `地域.apm.tencentcs.com:4317`）和 Token。
3. Token 只写在 Collector，不写网关：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
processors:
  batch: {}
exporters:
  otlp:
    endpoint: ap-guangzhou.apm.tencentcs.com:4317
    headers:
      Authorization: "Bearer ${APM_TOKEN}"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp]
```

地域、端口、鉴权头名以控制台当前说明为准。启动 Collector 前把 `${APM_TOKEN}` 换成真实 Token，或用环境变量注入。

### 阿里云 ARMS

控制台开通 **OpenTelemetry** 接入，复制 Endpoint 和鉴权头，整份结构与腾讯云相同，只改 exporter：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
processors:
  batch: {}
exporters:
  otlphttp:
    endpoint: https://<控制台给出的 ARMS OTLP 地址>
    headers:
      Authentication: "<控制台给出的鉴权值>"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlphttp]
```

头名、是否 HTTPS 以 ARMS 控制台为准。网关配置不变。

### Jaeger / Tempo

两者都原生收 OTLP，Collector 只做转发：

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
processors:
  batch: {}
exporters:
  otlp:
    endpoint: jaeger-collector:4317
    tls:
      insecure: true
    # 对接 Tempo 时改成：endpoint: tempo:4317
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp]
```

## 会打哪些 Span

| Span | 含义 |
|------|------|
| `gateway.request` | 整次请求（根 Span） |
| `gateway.auth` | 全局或路由认证 |
| `gateway.ratelimit` | 全局或路由限流 |
| `gateway.proxy` | 每一次上游 HTTP 调用（含重试，带节点与状态码） |

这是网关阶段耗时，不是 Java Agent 那种方法级调用树。函数级 CPU 热点仍用 pprof。

根 Span 会带：`gateway.trace_id`、`gateway.instance_id`、`http.request.method`、`http.route`、`http.response.status_code`。

---

## 和现有日志的关系

| 字段 | 用途 |
|------|------|
| 访问日志 / 后端追踪日志里的 `trace_id` | 网关控制台排查、请求重放 `X-Gateway-Replay-Trace-Id` |
| APM 里的 TraceId | W3C 128-bit，跨服务串联 |
| Span 属性 `gateway.trace_id` | 两边互查 |

不要用 APM TraceId 替换内部 `trace_id`。

---

## 注意

- 生产必须采样。全量上报会增加数据面延迟和 Collector 压力。
- `pass_headers` 白名单不会丢掉 `traceparent` / `tracestate`；追踪开启时会在转发前再次写入。
- 上报走批量异步，Collector 短暂不可用不应让网关失败；初始化 endpoint 非法会让进程启动失败。
- 上游服务也要识别 W3C `traceparent`（OpenTelemetry / SkyWalking 8+ 等），整条链路才能在 APM 里连成一棵树。
